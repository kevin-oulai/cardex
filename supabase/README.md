# CARDEX backend — Supabase foundation

This directory contains a **database foundation**, not a deployed backend. The live GitHub Pages game still runs locally until the Supabase project is connected and server-authoritative gameplay is integrated.

## Hosting choice

Use [Supabase](https://supabase.com/) Free: PostgreSQL, Auth, and Edge Functions. Free projects may pause after inactivity. Keep GitHub Pages for the frontend.

## Setup

1. Create a Supabase project in your own account. Choose an appropriate EU region for the expected audience.
2. In the Supabase SQL editor, run [001_foundation.sql](./001_foundation.sql).
3. Enable email/password authentication and configure the allowed Site URL and redirect URLs for `https://kevin-oulai.github.io/cardex/`.
4. Import **all 96** trusted vehicle catalog rows from `index.html` into `public.car_catalog` (the migration does **not** seed the catalog).
5. Add a trusted server process or Supabase Edge Function to issue cards, debit booster tickets, and create each day's shared UTC boss. Do **not** let the browser choose serials, create cards, or pick bosses.
6. Only then integrate the frontend with Supabase Auth and migrate existing local saves.

## Tables and trust boundaries

- `profiles`: private account profile, protected by owner-only row-level security.
- `car_catalog`: public, server-maintained stats used for scoring.
- `owned_cards`: individual cards with database-issued **unique serial numbers**; owners can read but **cannot mint**.
- `daily_bosses`: public UTC-date boss schedule; only the server can write.
- `showdown_scores`: public scores; clients cannot write arbitrary results.
- `submit_showdown(serial)`: authenticated SQL function validates ownership, computes score from trusted stats, and only improves the player's best result.

**Important:** A serial identifies a particular card, not necessarily a globally limited edition. Serial IDs are generated by the database. Existing browser-owned cards have **no trusted provenance**; importing them into competitive ownership or granting permanent serials requires an explicit anti-cheat/migration policy.

## Remaining implementation

- Authentication UI and session lifecycle; username handling and moderation.
- Secure booster issuance endpoint, ticket/credit ledger, transaction locking, rate limits, and abuse controls.
- Shared boss scheduler (with an atomic idempotent insert).
- Leaderboard UI (daily/all-time definitions), privacy-aware public display names, pagination, moderation.
- Save migration strategy and reconciliation with local collections.
- Deployment and end-to-end tests using real Supabase credentials supplied through secure configuration, **never committed**.
- Update privacy and legal pages **before enabling accounts or processing account emails**. Determine GDPR controller contact, retention, deletion/export workflows, processors, and any required notices.

## Security caveat

This SQL is a first-pass scaffold, not a security audit. It has not been executed against a live Supabase instance. Review and test RLS and privileges in a staging project before opening registration. Database functions use `security definer` and must remain tightly scoped.
